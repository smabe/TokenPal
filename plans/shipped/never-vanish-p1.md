# never-vanish-p1 — visible-surface invariant: buddy or chat is always on screen

You are phase `p1` of the `never-vanish` plan. This phase makes the Qt overlay enforce one rule at every visibility transition — if the buddy is hidden, chat is shown; if chat is being hidden while the buddy is hidden, the buddy is shown — and reset an all-hidden persisted state to the buddy at restore, so the running app can never have zero surfaces on screen. One commit.

## Locked decisions
See the master `plans/never-vanish.md`. The decisions binding this phase:
- Anchor set is exactly {buddy, chat}. News is not an anchor and is never touched by the rule (operator: "when the buddy is hidden we need to automatically show the chat window"; "if we're in chat window only mode and we hide the chat window the app is also gone but still running", 2026-09-06).
- The rule lives in `QtOverlay` only. `tokenpal/config/ui_state.py` stays a codec with no knowledge of the rule; the repaired state reaches disk through the normal persist path.
- Launch repair resets to the default: a persisted `{buddy_visible: false, windows.chat: false}` restores with the buddy shown and chat left hidden, and the repair marks the state dirty so `teardown()`'s flush writes it back even if the user never toggles. *(Operator sign-off 2026-09-06: "reset to the buddy" — chosen over applying the runtime rule, which would have shown chat.)*
- Assert with `isHidden()`, never `isVisible()` — headless Qt on macOS auto-hides translucent windows between pumps (`tests/test_qt_overlay.py:180-186`). Unit tests never assert focus.

## Decisions & findings
### Decision: enforce in the overlay's transitions and restore, not in `ui_state.py`  *(status: active)*
- **Rationale:** every path that can produce the all-hidden state — tray, right-click menu, history Hide button, `/chatlog`, and the persisted file via `restore_visibility_state` — ends in `_toggle_buddy`, `_do_toggle_chat`, or `restore_visibility_state` (`tokenpal/ui/qt/overlay.py:498-514`, `:1461-1466`, `tokenpal/ui/qt/_log_window.py:113-117`, `tokenpal/app.py:676-678` → `toggle_chat_log` `overlay.py:725`, `tokenpal/app.py:255-261`). Enforcing at those three points is binding for every caller, including tests that call `restore_visibility_state` directly; a repair in `load_ui_state` would cover only the file.
- **Alternatives considered:** repair in `load_ui_state` (pure, easy to test, but bypassable by any direct `restore_visibility_state` caller and duplicates the rule once the overlay enforces it at runtime); refuse the hide (no-op) instead of swapping — rejected by the operator's words, which describe a swap.
- **Evidence:** the citations above; the investigator confirmed nothing in `tokenpal/brain` reads visibility; the historical reviewer confirmed "neither window is coupled" (`097ee22`) was a structural statement, never a bug fix, so no prior coupling attempt is being re-litigated.

### Decision: auto-shown chat must take the real show path  *(status: active)*
- **Rationale:** an embedded dock's `QLineEdit` drops keystrokes unless the history `NSWindow` is activated and `focus_input()` runs (`overlay.py:474-481`, `:1325-1340`). Reusing `_set_window_visible` (show + `apply_macos_stay_visible` + raise + activate) and letting the existing activate/focus block fire keeps one code path for "chat appears". All three activations run synchronously in one event-loop slot, so there is no empty frame between hide and show.
- **Alternatives considered:** flipping `_user_visible["chat"]` and calling `window.show()` inline — would skip `apply_macos_stay_visible` and the tray relabel.
- **Evidence:** `overlay.py:1243-1247`, `:1325-1340`; UI specialist and interaction reviewer 2026-09-06.

## Failure modes to anticipate
- Re-entrancy: `_set_buddy_visible(False)` calls `_set_window_visible(chat, True)` which never calls back into buddy; `_do_toggle_chat` hide calls `_set_buddy_visible(True)` which never touches chat. No `hideEvent`/`closeEvent` on `ChatHistoryWindow` re-enters the toggle (only the Hide button does, `_log_window.py:113`). Keep it that way — a "show" must never trigger the other surface's hide.
- **The macOS re-map bug class.** Four prior commits (`98823c3`, `c357b5e`, `2e05131`, `60c00c4`) each fixed a surface that appeared but lost its platform hook (`apply_macos_stay_visible` / click-through / key window) on a *re-show*, caught only by clicking another app or switching Spaces. The two auto-show transitions here are exactly that shape, which is why the Done captures include a click-away and a Space switch.
- Persist coalescing: both auto-show paths call `_persist_ui_state()` twice within 250 ms; that is the designed debounce (`overlay.py:1025-1036`), not a bug. Tests must `flush_pending_persist()` before asserting the saved dict.
- The `_toggle_buddy` closure captures nothing but `self`; when lifting it, keep the `self._buddy is None` early return so `run_loop`-less test overlays behave.
- Tray labels: `BuddyTrayIcon` mutates one `QMenu` shared by the tray and the buddy right-click (`tokenpal/ui/qt/tray.py:87-97`, `overlay.py:1461-1466`); the relabel calls already inside `_set_buddy_visible`/`_set_window_visible` are sufficient — do not add a second relabel.
- The history window is never `move()`d (`_log_window.py:54` only resizes; only the dock moves, `overlay.py:1419,1429`), so an auto-shown history appears at its last position, or at Cocoa's default on first-ever show. Pre-existing; the capture is judged on presence and focus, not position.
- The tray's Quit (`overlay.py:493-495`, direct `app.quit()`) bypasses `teardown()` and its persist flush today; unchanged by this phase (parking lot). Quit for the Done criteria via Ctrl-C in the terminal, which runs `_shutdown` → `teardown` (`tokenpal/app.py:1826-1830`).
- On the operator's Mac, never run the buddy from a Claude Code shell for the capture (Control Center poisoning — see master Background findings). Use `open -na Ghostty.app --args -e <repo>/run.sh`.
