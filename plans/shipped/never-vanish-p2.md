# never-vanish-p2 — own bundle identity on macOS, launched through LaunchServices

You are phase `p2` of the `never-vanish` plan. This phase gives the Qt overlay its own macOS identity: on macOS, `tokenpal` builds `~/.tokenpal/TokenPal.app` (bundle id `com.tokenpal.app`) around the Python framework stub and relaunches itself through `open`, so the menu bar item is attributed to TokenPal and never to the terminal that started it. One commit.

## Locked decisions
See the master `plans/never-vanish.md`. The decisions binding this phase:
- Bundle id `com.tokenpal.app`, bundle name `TokenPal`, location `<data_dir>/TokenPal.app` (data dir resolved at `tokenpal/app.py:143`; default `~/.tokenpal`, `tokenpal/config/schema.py:229`). Constant across venv rebuilds and Homebrew upgrades — Control Center keys its records on the Info.plist id alone: a copied stub whose code signature still says `org.python.python` was placed at `(1487, 7)` under its own Info.plist id (probe 2026-09-06). No re-signing step.
- The relaunch decision lives in `tokenpal.app:main`, after the first-run wizard and before `discover_senses`, so every entry point (`run.sh:47`, `scripts/install-macos.sh:656`, bare `tokenpal`) is covered and the wizard still runs in the terminal with stdin. `--check`, `--validate`, `--version` never relaunch (they exit before the decision point, `tokenpal/app.py:138-152`).
- Only the Qt overlay relaunches: darwin, resolved overlay name `qt`, and not already inside the bundle. Textual/console/`TOKENPAL_HEADLESS=1` (`tokenpal/ui/registry.py:_qt_unavailable_reason`, `:21`) stay in-process.
- Launch is `open -W --env TOKENPAL_IN_BUNDLE=1 --env TOKENPAL_LAUNCH_CWD=<parent cwd> --stdout <T1> --stderr <T2> <bundle> --args -m tokenpal <original argv> --skip-welcome`. *(The `TOKENPAL_IN_BUNDLE` marker was added at review: it is the only identity check that needs no pyobjc, and `main()` **consumes** both variables rather than reading them, so a terminal the buddy opens cannot inherit a marker claiming to be the bundle.)* `<Tn>` is `os.ttyname(n)` when `os.isatty(n)` (per fd — stdout and stderr decided separately), else `<data_dir>/logs/tokenpal-bundle.log`, which the parent truncates before launching. No `-n`: one instance. The already-running check runs **before** `ensure_bundle`, so a rebuild can never `rmtree` a live app's tree.
- Ctrl-C in the terminal quits the buddy through the app's existing shutdown path: the parent runs `open` with `subprocess.Popen`, catches `KeyboardInterrupt`, sends `SIGINT` to every running instance (so `_shutdown` at `tokenpal/app.py:1826-1830` schedules `overlay.teardown()` and the persist flush as today), polls for up to 5 s, then `forceTerminate()`, then waits for `open`. **Corrected at review:** a pid of `-1` (an instance with no live process) is skipped, because `os.kill(-1, ...)` signals every process the user owns; liveness is polled with `os.kill(pid, 0)`, never `isTerminated()`, whose value is cached until the main run loop turns and this parent never turns one; and SIGHUP/SIGTERM route into the same path, because the buddy is launchd-parented and closing the terminal would otherwise orphan it. `subprocess.run` is not used — it SIGKILLs `open` inside its own `KeyboardInterrupt` handling before ours runs.
- The child restores the parent's working directory: `main()` begins with `if cwd := macos_bundle.consume_launch_env(): os.chdir(cwd)` before `load_config` — and reports a failed `chdir` rather than swallowing it, because cwd is load-bearing for path containment — so the repo-local `config.toml` fallback (`tokenpal/config/paths.py:22-25`, `tokenpal/config/loader.py:133`), `git_root(Path.cwd())` for `find_files`/`open_path` (`tokenpal/util/paths.py:62,177-178`), `grep_codebase` (`tokenpal/actions/grep_codebase.py:154`) and `git_log` (`tokenpal/actions/git_log.py:20`) see the same cwd as a terminal run. `--config` needs no rewrite because of this.
- Venv discovery inside the bundle uses `Contents/pyvenv.cfg` + `Contents/lib/python3.X/site-packages` → venv purelib symlink (probe: PySide6 6.11.0 and editable `tokenpal` import this way, also under a path with spaces; the `__PYVENV_LAUNCHER__` env alternative is rejected because it makes the bundle depend on its launcher's environment).
- Fallback: if the framework stub does not exist (non-framework Python: uv-managed, pyenv without `--enable-framework`), **if pyobjc is not installed** (added at review — without it the parent can neither see nor quit the child it launched), if building raises `OSError`, or if `open` returns non-zero, log one warning naming the reason and continue in-process exactly as today. `relaunch_in_bundle` raises `RuntimeError` on a non-zero `open` return so the same `except` covers it. Never crash on the bundle path.
- Under the bundle, `responsible_host()` returns `"TokenPal"`. The bundle check precedes the `TERM_PROGRAM` read because `open` passes the shell's environment through.

## Decisions & findings
### Decision: relaunch in `app.main`, not in `run.sh`  *(status: active)*
- **Rationale:** three launchers converge on `main()` (`run.sh:47`, `scripts/install-macos.sh:656`, the `tokenpal` console script `pyproject.toml:87`); the wizard needs the terminal's stdin and runs before the decision; the fallback logic needs Python.
- **Alternatives considered:** `open` from `run.sh` — leaves bare `tokenpal` and the installer on the shared identity; `NSWorkspace.openApplicationAtURL:` — returns the `NSRunningApplication` directly but has no stdout redirect, so `./run.sh --verbose` would lose its terminal output.
- **Evidence:** `tokenpal/app.py:135-239`; `open` probes 2026-09-06 (master Background findings).

### Decision: copy the framework stub instead of symlinking it  *(status: active)*
- **Rationale:** both work (specialist probe), but a copy survives a Homebrew upgrade that removes the old Cellar path until the stamp triggers a rebuild, instead of a dangling symlink that fails at `open` time.
- **Evidence:** `otool -l` shows absolute `LC_LOAD_DYLIB` to the Cellar path, so the copy loads the same framework.

### Decision: Ctrl-C forwards SIGINT, not `terminate()`  *(status: active)*
- **Rationale:** `terminate()` delivers a Quit Apple event that Qt turns into `app.quit()`, bypassing `_shutdown` (`tokenpal/app.py:1826-1830`) which is the only path that runs `overlay.teardown()` → `flush_pending_persist()` (`tokenpal/ui/qt/overlay.py:985-995`, measured at b12119b). SIGINT to the child's pid keeps that path intact.
- **Evidence:** historical reviewer 2026-09-06 (commits `1e3acde`, `e9e5f60`, `3484a06`); `subprocess.run` kill-on-exception in CPython's `subprocess.py`.

### Finding: `open -W` semantics (probed 2026-09-06)
- Returns 0 even when the child exits non-zero; prints "Unable to block on applications" and returns 1 if the child exits before `open` attaches (sub-second). SIGINT to `open` kills nothing. `--stdout` must be a real path; `/dev/fd/1` fails with `-10810`. `--env` is delivered to the child.

### Finding: Control Center keys on the Info.plist id (probed 2026-09-06)
- A byte copy of the Python.app stub inside `StubPlain.app` (Info.plist id `com.tokenpal.probe.stubplain`, `codesign -dv` still `Identifier=org.python.python`) launched with `open` was placed at `(1487, 7)` and painted; `NSBundle.mainBundle().bundleIdentifier()` reported the Info.plist id and `sys.prefix` the bundle's `Contents`. `codesign --force` on the bundle fails ("In subcomponent: …/Contents/pyvenv.cfg"), so signing is neither needed nor easy.

### Decision: build the bundle into a sibling temp directory and `os.replace` it into place  *(status: active — carried in from p1's review)*
- **Rationale:** the shard's `ensure_bundle` as drafted does `shutil.rmtree` + recreate-in-place, with a stamp file written last so a bad prior build is detected. If the process dies between the `rmtree` and the stamp — crash, force quit, OOM — `TokenPal.app` is left half-built with no stamp, and the next `relaunch_in_bundle` hands that broken bundle to `open`. The repo already solves exactly this three times over and never in-place: `tokenpal/config/toml_writer.py:37-39` (`tmp = path.with_suffix(".tmp")` → `os.replace`), `tokenpal/server/job_store.py:50-54` (`tempfile.mkstemp` → `os.replace`), `tokenpal/audio/deps.py:180-186` (`dest.tmp` → `tmp.replace(dest)`). Build into a sibling temp directory, then `os.replace` it over the old bundle; keep the stamp as the *content* identity check (Python version, cdhash) it is needed for, not as partial-build recovery.
- **Evidence:** p1 review round 1, reuse angle, 2026-09-06; the three call sites above read this session.
- **Note for the worker:** `os.replace` on a directory requires the destination to be an empty directory or absent — rename the old bundle aside and delete it after the swap, or remove it immediately before the rename and accept a much smaller window than the current design's.

### Review round 1 (host-native fan-out, 6 angles, 2026-09-06) — accepted and fixed
Codex peer still out of quota, so `/auto-review high` took the same-family fallback again: 6 parallel angles (line-by-line, removed-behavior, cross-file, security boundary, quality, tests+conventions) plus a closing round. **No external-peer receipt for p2 either, and no `peer-review.sh stamp`.**

- **`os.kill(-1, SIGINT)` could have signalled the operator's whole login session.** `NSRunningApplication.processIdentifier` returns `-1` for an app with no live process (Apple docs, `appkit/nsrunningapplication/processidentifier.md`), and `kill(2)` with `pid == -1` sends the signal to *every* process with the user's uid. `kill` succeeds, so the surrounding `except OSError` never fires and nothing is logged. Trigger: quit the buddy from the tray, then press Ctrl-C in the launching terminal — the lookup returns a stale instance whose pid has gone to `-1`. Found independently by two angles. Fixed with `_instance_pids()`, which drops any pid `<= 0`.
- **`isTerminated()` is a cached value here, so Ctrl-C would have force-killed a buddy that already exited cleanly.** `NSRunningApplication`'s overview states its properties are refreshed only "until the next turn of the main run loop in a common mode" and that polling without letting the run loop run keeps returning the stale value. The parent is a plain CLI process that never turns a run loop, so the 5 s poll would read `False` throughout and then `forceTerminate()` — the SIGKILL-equivalent this whole SIGINT contract exists to avoid, landing before `memory.teardown()`'s sqlite close and the session-summary write. Replaced with `_alive(pid)` (`os.kill(pid, 0)`), which needs no run loop, and the loop now sleeps before re-filtering so a process that exits on the last poll is not force-quit.
- **A pyobjc-less install would hang on launch, forever.** `pyproject.toml` makes `macos` (pyobjc) a separate extra from `desktop` (PySide6), so `pip install -e .[desktop]` is a supported state. Both identity guards fail *open* on `ImportError` — `running_in_bundle()` → `False`, `running_instances()` → `[]` — so the bundled child re-entered the relaunch gate and ran `open -W` on the app it already was. `open` is deliberately without `-n`, and `man open(1)` says `-W` waits for the applications it opens "(or that were already open)" to exit: the child blocks on itself, no buddy appears, and both processes had already torn down their log handlers. Found independently by three angles. Fixed with an `IN_BUNDLE_ENV` marker passed as a second `--env` and checked first in `running_in_bundle()` — the one identity check that needs no pyobjc.
- **A failed swap deleted the last working bundle.** `ensure_bundle`'s `finally` unconditionally `rmtree`d both `staging` and `retired`, so a rebuild that got past `os.replace(bundle, retired)` and then failed left no bundle at all — plus a TCC grant bound to a deleted cdhash. The mid-build test covered only a *first* build, never a rebuild over a good bundle, which is exactly the case the staging decision was written for. Fixed by restoring `retired` on a failed swap, with a test that rebuilds over a good bundle and fails the second rename.
- **The redirect log was world-readable.** `log_path.open("w")` under umask 022 gives 0644, while `setup_logging` explicitly chmods `tokenpal.log` to 0600 and CLAUDE.md's Privacy section states "Log files and memory.db at 0o600". That file carries the child's entire stdout+stderr — under `--verbose`, the whole DEBUG stream including app names and sanitized window titles. Fixed with `chmod(0o600)`.
- **Closing the terminal orphaned the buddy — a regression.** Before this phase the buddy was a child of the shell and died with it; now it is launchd-parented and only the blocking parent ties it to the terminal, and only `KeyboardInterrupt` quit it. A closed window (SIGHUP) or a `kill` left a buddy running, still writing into a `/dev/ttysNNN` that a later session may be handed. Fixed by routing SIGHUP/SIGTERM into the same shutdown path, restoring the previous handlers in a `finally`.
- **The parent's own logging went nowhere on the success path.** Closing and removing the `tokenpal` handlers before `open` left only `logging.lastResort` (WARNING to stderr), so `"Built <bundle>"` and `"Launching <bundle> via open"` — the only record a relaunch leaves, and the only trace of a rebuild triggered by a Homebrew upgrade — were discarded, in the one file the installers tell users to read. Fixed by adding a stderr handler for the parent's remaining life and removing it again on the in-process fallback.
- **The cwd restore was an unconditional, silently-failing `chdir` from ordinary inherited environment.** It ran on every platform and every subcommand, gated on nothing, and the cwd it sets is load-bearing for the privacy contract — `util/paths.py` derives `git_root(Path.cwd())` as a containment root for `find_files`/`open_path`. Now gated on `running_in_bundle()` and it prints on failure instead of leaving the buddy silently rooted at `/`.
- **`--validate` gave the wrong permission advice under `--overlay`.** `_runs_as_bundle_app` read `config.ui` alone while the real gate reads `config.ui` overridden by `args.overlay`, and `run_validate` never received the flag. `tokenpal --validate --overlay textual` on a qt config told the user to grant Screen Recording to "TokenPal" for a run that would use Textual and need the terminal's grant. Fixed by threading `overlay_override` through and by making both sites call one predicate.
- **The predicate was written twice with different conditions.** `main()`'s inline gate and `cli.py`'s `_runs_as_bundle_app` answered the same question — will this launch end up on `com.tokenpal.app`? — with different tests, guaranteeing future drift between the behavior and the advice about it. Collapsed into `macos_bundle.would_use_bundle(ui_config)`, which is also the first automated coverage of the gate: `--overlay textual` and `--overlay console` are now pinned as non-relaunching.
- **`docs/claude/ui.md` named the wrong tray-showing function.** `qt/app.py:build_shell` only *constructs* `BuddyTrayIcon`; `run()`'s `__main__` guard is what shows it, which is why `tests/test_qt_shell.py` can safely call `build_shell` directly. Corrected. `permissions.py`'s module docstring also still claimed grants attach to the terminal; corrected. `BUNDLE_NAME` is exported so the display name is not re-typed in four places.

### Review round 1 — refuted or parked
- **"`open -W`'s non-zero return might be a normal app exit, so raising `RuntimeError` could restart the buddy."** Refuted: probed this session and recorded in the master's Background findings — `open -W` returns 0 even when the child exits non-zero, and 1 only when the child dies before `open` attaches, which is precisely the broken-bundle case. The worker had already found and fixed the related real defect (a deliberate Ctrl-C must not consult `returncode`, or the fallback would restart the buddy the user just stopped).
- **The bundle turns a TCC grant into a general-purpose interpreter capability.** Real, and worth the operator knowing: `Contents/MacOS/TokenPal` is a copy of the Python stub, so anything that can run `open ~/.tokenpal/TokenPal.app --args -c '<python>'` inherits whatever Screen Recording / Accessibility / Microphone grants the user gave "TokenPal", with no prompt. This is inherent to the locked design — a shebang wrapper does not work (the kernel execs the interpreter and the main bundle becomes Python.app, probed 2026-09-06), and re-signing fails on `Contents/pyvenv.cfg`. It is not clearly worse than the status quo it replaces, where the grant sits on the user's terminal and every process run from that terminal inherits it. **Parked and surfaced to the operator** rather than silently redesigned.
- **The kokoro TTS worker is spawned with `sys.executable`, which is now the bundle stub.** If such a worker registered with LaunchServices it would appear in `running_instances()` and could both block a later launch ("TokenPal is already running") and be force-quit by the Ctrl-C path. `[unverified]` — the worker is spawned with `subprocess.Popen`, not through LaunchServices, which is normally what registers an app, and confirming it would mean launching the bundle. Parked with the mitigation named (spawn workers from `sys._base_executable`).
- **The single-instance guard is machine-wide**, so a second checkout with its own `--config`/`data_dir` is declined with "TokenPal is already running" and exit 0. That is the locked `open`-without-`-n` design; Windows/Linux still allow two buddies. Parked.
- **Non-tty stdout is redirected to the log file**, so `./run.sh --verbose | grep sense` loses its output. Forced by `open`: `--stdout` needs a real path and `/dev/fd/N` fails with -10810 because launchd spawns the app. Mitigated rather than fixed — the parent now prints where the output went.
- **`relaunch_in_bundle` always returns 0**, so a child that dies at startup no longer surfaces a non-zero exit to a wrapper script. Inherent to `open -W`. Parked.
- **Orphaned `.TokenPal.app.tmp-*` staging dirs** survive a SIGKILL between `mkdtemp` and the `finally`; nothing sweeps them. A sweep risks deleting a concurrent launch's staging tree, so it is parked rather than guessed at.
- **`_package_version()` duplicates `cli.py:print_version`'s three-line lookup.** Parked: the two live in modules that must not import each other (`cli` would drag the CLI into the bundle module), and a shared home for three lines is not yet earned.

### Review round 2 (closing round over the repaired diff) — accepted and fixed
- **The launch marker leaked into every terminal the buddy opens.** `open_app`'s allowlist includes Terminal, iTerm, Ghostty and Cursor, and `open` hands the child the buddy's environment, so `TOKENPAL_IN_BUNDLE=1` would persist in that terminal and in every shell in it. A later `tokenpal` from there would answer "I am already the bundle", skip the relaunch, and file its status item under `org.python.python` — this feature's own bug, made silent and sticky. Fixed by *consuming* the hand-off: `consume_launch_env()` pops both variables and latches the answer for this process.
- **The SIGHUP/SIGTERM fix did not hold on the install it was written for.** `_quit_running_instances` needs `running_instances()`, which returns `[]` without pyobjc — so on a pyobjc-less install the terminal closing still orphaned the buddy, and the next launch's already-running guard was blind too, so it ran `open -W` against the live instance and blocked. Fixed at the root: **pyobjc is now required on the bundle path**, via `bundle_unavailable_reason()`, which mirrors `registry.py`'s `_qt_unavailable_reason` idiom. Without it we can neither recognise nor quit the child we launched, so relaunching was never safe there.
- **A failed *restore* deleted the last copy.** The repair added `os.replace(retired, bundle)` when the swap fails, but the `finally` then swept `retired` unconditionally — and whatever makes the swap fail usually makes the restore fail too. Verified empirically by the reviewer: both renames failing left the data dir empty. The sweep is now conditional on `bundle.exists()`.
- **`would_use_bundle` had silently swallowed a diagnostic.** The old inline gate let a non-framework interpreter reach `ensure_bundle`, whose `RuntimeError` surfaced as `log.warning("running in-process: ...")`. Folding the stub check into the predicate removed that path, so the population most likely to hit the parked-item bug got no explanation. `main()` now logs the reason at INFO whenever a darwin/qt launch declines the bundle.
- **`signal.signal(sig, None)` is a TypeError.** `getsignal` returns None for a handler not installed from Python, so the restore in the `finally` could have replaced the shutdown's `return 0` with a traceback. Skipped on None. A second SIGHUP/SIGTERM arriving during the shutdown sequence is now suppressed rather than escaping as an unhandled `KeyboardInterrupt`.
- **The cwd gate guarded nothing.** `TOKENPAL_LAUNCH_CWD` is only ever inherited alongside `TOKENPAL_IN_BUNDLE`, so gating the chdir on `running_in_bundle()` could not block a stray value — but it added a way for the restore to be skipped if the marker were ever lost while the cwd survived. Consuming both together makes the gate unnecessary, and the unconditional form is restored.
- **Smaller fixes:** the parent's stderr handler had no formatter and a hardcoded INFO level (it now shares `LOG_FORMAT`/`LOG_DATEFMT` with `setup_logging` and honours `--verbose`); `_instance_pids` also catches `AttributeError` from a pyobjc object; `cli.py`'s two remaining `"TokenPal"` literals now interpolate `BUNDLE_NAME`; `docs/claude/ui.md`, this shard's Locked decisions, the module docstring and `ensure_bundle`'s docstring were all corrected to describe the shipped design; and an autouse fixture clears the marker and its latch so no identity test can inherit either.

## Failure modes to anticipate
- **Permissions re-grant, and it recurs.** First run after this phase, macOS prompts for Screen Recording (and Accessibility / Microphone if used) for "TokenPal"; Screen Recording takes effect only after the app restarts. TCC's requirement for an ad-hoc-signed binary is bound to its cdhash, so every stub rebuild (Homebrew Python upgrade, Python minor bump) invalidates the grant and the prompt returns. Expected; the `--validate` wording is the mitigation.
- **Non-framework Python** (uv-managed, pyenv without `--enable-framework`): `framework_stub()` is None → in-process fallback with a warning. The three non-Mac target machines are unaffected (darwin gate).
- **Stub path churn**: Homebrew minor upgrades change the Cellar path; the stamp includes the resolved stub path and mtime → rebuild. A Python minor bump changes `lib/python3.X` → rebuild by the version in the stamp.
- **Environment through `open`**: PATH/HOME/TERM/TERM_PROGRAM are inherited (probe); cwd is restored by the child from `TOKENPAL_LAUNCH_CWD`.
- **Workers spawned with `sys.executable`** (`tokenpal/audio/backends/kokoro.py:67`, `tokenpal/audio/deps.py:99`) now run the bundle stub; they inherit `pyvenv.cfg` discovery through the bundle and create no status item. Nothing to change; verify with `tokenpal --check` inside the bundle if audio is enabled.
- **Log file redirect**: only non-tty launches hit `tokenpal-bundle.log`; the parent truncates it per launch, so it never grows across runs (whether `open` itself truncates is unverified — `man open` does not say).
- **Never test the tray from a Claude Code shell on the operator's Mac.** The AX/placement Done criterion is run from a Ghostty window (`open -na Ghostty.app --args -e <repo>/run.sh`). A unit test that `show()`s a real `QSystemTrayIcon` from pytest run in that shell poisons the registry; none may exist (today's suite constructs `BuddyTrayIcon` in `setup()` but only `run_loop` calls `show()`, `overlay.py:530` at b12119b).
- `app.py` is a 122-commit file; keep the relaunch block to the one insertion point above and do not reorder the memory/sense setup that follows it.
