# desktop-content-contract-p3 — `--validate` permission rows, registry invariants test, docs

You are phase `p3` of the `desktop-content-contract` plan. This phase delivers, as one commit, the read-only macOS permission probes and their `--validate` rows, the registry-driven invariants test that every future marked action must pass, and the documentation that tells a tool author what the contract is.

## Locked decisions
See the master `plans/desktop-content-contract.md`. The decisions binding this phase:
- Probes never prompt: `HIServices.AXIsProcessTrusted()` (already used at `tokenpal/senses/_keyboard_bus.py:33-37`) and `Quartz.CGPreflightScreenCaptureAccess()` (Apple: preflight is non-prompting, https://developer.apple.com/documentation/coregraphics/cgpreflightscreencaptureaccess(); probed from the repo venv 2026-09-02 with no dialog). `CGRequestScreenCaptureAccess` is never called.
- A missing Screen Recording grant is a warning row, not a counted problem; a missing Accessibility grant stays a warning too (today's block is a warning, `tokenpal/cli.py:408-414`).
- Off macOS, one row: `desktop tools: no OS permission grants needed`.

## Decisions & findings
### Decision: static invariants in the shared test, behavior in per-tool tests  *(status: active)*
- **Rationale:** a generic test cannot call an unknown tool with valid arguments or fake its OS read, so the shared test pins what is checkable from the class alone plus the one dynamic rule the contract fixes as order-independent of arguments (consent first). Refusal and no-leak over the real read path are each tool's own tests, with `assert_no_leak` (p2) as the shared assertion. Issue #51 asked for all four checks in the parametrized test; this narrows it, is recorded in the master's Locked decisions, and is surfaced at approval.
- **Evidence:** `AbstractAction.execute(**kwargs)` (`tokenpal/actions/base.py:68-70`) carries no argument metadata beyond the JSON schema.

### Decision: probes live in `tokenpal/desktop/`, not `cli.py`  *(status: active)*
- **Rationale:** #52 (selected text) and #55 (OCR) need the same answers at runtime to explain a failed read; `cli.py` is not importable from a tool.
- **Evidence:** `_keyboard_bus.py:23-39` already duplicates the Accessibility call for its own reason (warmup); parked as adjacent in the master.

### Finding: the first contract test passed a composite unsafe tool  *(status: resolved)*
- Built as a plausible #55 OCR tool by an adversarial reviewer, it captured the screen before checking consent, shipped the text off-box through `HttpBackend` (whose `[llm] api_url` may be a remote GPU host), skipped consent entirely on one branch of its `kind=` argument, hand-built the envelope so a forged `</desktop_content>` escaped it, logged the text, and returned it as `display_text`. It reported **7 passed**. A separate unmarked tool — one that forgets `reads_desktop_content` and is therefore invisible to the test *and* to every runtime gate, since they read the same flag — also passed.
- **Resolution, five hardenings, each verified to fire on a constructed violation and to stay quiet on a compliant tool:** a marker heuristic (anything reaching `tokenpal.desktop.content`, recursively through `tokenpal.actions.`, must declare the marker); a stricter network rule for marked tools only (full `tokenpal.` closure, since the registry-wide narrow walk exists to avoid false-flagging local tools but a marked tool should touch no client at all); consent re-checked for every declared argument shape including each enum value; relative imports resolved rather than dropped; and the envelope check made two-sided — no non-docstring string literal in the tool's own modules may contain `desktop_content`, and `to_prompt_block` must be called.
- **Two false positives found and fixed during that work:** the literal scan initially walked the whole import closure and so flagged `tokenpal/desktop/content.py`, which legitimately owns the tag; and a docstring quoting the docs' own "never hand-build the envelope" rule failed a compliant tool until the scan excluded docstrings.

### Finding: six documentation claims were false  *(status: resolved)*
- The section is what #52-#55 authors build against, so each claim was checked against source rather than transcribed. Wrong as first written: `require_consent()`'s `None` return omitted (so `return require_consent()` reads as correct and breaks on a consented machine); "results are never cached" stated run-wide when the exemption is per-tool; the same-batch skip stated as absolute when it is order-dependent; `cacheable` and the consent call listed as inherited when `AbstractAction.cacheable` defaults `True` and nothing calls consent for you; the anonymous-refusal rationale citing a DEBUG-log path unreachable for a marked tool; and `CLAUDE.md` claiming three runtime exclusions where only the conversation path has one.
- A correction pass introduced its own error, caught on re-verification: "the wellness and messaging terms drop out" is wrong in both directions — `whatsapp`/`telegram` stay, while `chase` and `fidelity` drop. The docstring now says plainly that the narrow list is not a superset of banking coverage.

## Failure modes to anticipate
- `Quartz` import cost: pyobjc's Quartz binding takes noticeable time to import; keep the import inside the function so `tokenpal --check` and normal startup do not pay it.
- On macOS, `CGPreflightScreenCaptureAccess` reflects the TCC state for the *host binary* (the Python interpreter or the app bundle). Running from a terminal, the grant attaches to the terminal app or to `python`; that is why the header line names `sys.executable`.
- `discover_actions()` imports every module under `tokenpal.actions`; the invariants test must run it once (module-level or fixture), and it must tolerate platform-gated actions that are registered but not constructible on the test host — instantiate with `{}` inside a `try` and skip with a reason if construction raises.
- The Windows row is verified on the AMD desktop per the author-on-target-host rule; the test covers the branch, the run covers the reality.

### Carried in from the p2 review  *(added 2026-09-02)*
- **The registry-invariants test must also pin registry/catalog parity.** `_needs_consent` (`tokenpal/brain/agent.py`) is the exfiltration gate: it drops consent-gated tools once desktop content is in context, and it decides "gated" by looking the tool up in `tokenpal/actions/catalog.py`. A network action registered with `@register_action` but missing from the catalog returns `None` from `find_entry`, is treated as ungated, and stays available for the rest of a flagged run. Two reviewers verified that all currently registered actions do have entries, so this is latent, not live. Add to `test_privacy_contract.py`: every name in `_ACTION_REGISTRY` resolves via `find_entry`, and every action whose module imports `aiohttp`/`httpx`/`http_json` has a non-empty `consent_category`.
- **CLOSED in p2 — do not redo.** `tokenpal/app.py::_agent_log` was extracted to a module-level `make_agent_log(overlay)` factory and covered by `tests/test_agent_log_sink.py`. Mutation testing had shown both halves of its `persist` branch could be deleted with the suite still green; they are pinned now. Listed here only so p3 does not re-open it.
- **The agent-only invariant now has two enforcement mechanisms.** The orchestrator filters `reads_desktop_content` out of the conversation specs explicitly, but `tokenpal/brain/idle_tools_m3.py`'s `_build_tool_specs` builds from the fixed `M3_CATALOG` allowlist and consults no marker. Safe today because the allowlist is hand-written, but adding a marked tool to `M3_CATALOG` would route its output into the observation/comment path, which IS persisted. The registry-invariants test should assert no marked action appears in `M3_CATALOG` or in any `M1_RULES` `tool_name`/`extra_tool_names`.
- **Console and tkinter overlays discard a flagged run's answer.** `AbstractOverlay.log_buddy_message` is a no-op and only Qt and Textual override it, so under `--overlay console` or the tkinter fallback the unpersisted final answer goes nowhere while the bubble still points at a chat log that overlay does not have. Latent until a content tool ships. The docs section should state that desktop-content tools assume an overlay with a chat log.
