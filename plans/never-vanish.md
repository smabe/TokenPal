## Goal
Two things the operator asked for on 2026-09-06 after the menu bar icon vanished: the Qt UI must never reach a state with nothing on screen ("when the buddy is hidden we need to automatically show the chat window … if we're in chat window only mode and we hide the chat window the app is also gone but still running"), and the macOS menu bar item must stop depending on the shared `org.python.python` identity that let another app's Control Center record hide it.

## Scope contract
- **Requested outcome:** (1) hiding the buddy auto-shows the chat window; hiding the chat window while the buddy is hidden shows the buddy instead; a persisted `.ui_state.json` with both hidden is repaired at launch so something is on screen. - **Named semantic boundary:** Qt overlay surface visibility (buddy window, chat dock+history) and its persistence in `.ui_state.json`; the macOS launch path/process identity of the Qt overlay.
- **Explicit inclusions:** buddy window, chat window (dock + history), tray menu labels, `.ui_state.json` load/save, `run.sh` and the macOS installer's launch path, `apply_macos_accessory_mode`.
- **Explicit exclusions:** the news window is NOT an anchor surface (operator named only buddy and chat); Windows/Linux launch paths; tray icon artwork; Textual/console/tkinter overlays.
- **Intent class:** bounded outcome.

## Background findings
- **Root cause of the vanished icon (2026-09-06, verified by probe).** macOS 26 Control Center keeps a per-app registry at `~/Library/Group Containers/group.com.apple.controlcenter/Library/Preferences/group.com.apple.controlcenter.plist` → `trackedApplications` (bplist list of `{location, menuItemLocations, isAllowed}`). A status item is attributed to the *launching* app — the LaunchServices coalition the process runs in, which a terminal-spawned process inherits and an `open`-launched app gets fresh; `responsibility_get_pid_responsible_for_pid` returned self for every launch mode and is not the discriminator — and the item's bundle id is appended to that app's `menuItemLocations`. When a bundle id is claimed by a record that does not match the launcher, or by a DENY record, the item is parked off-screen — AX position `y≈1317` or `(2025, -1)` — while `QSystemTrayIcon.isVisible()` still reports True. The same Swift binary is placed at `y=7` as `com.tokenpal.pyid2` and parked as `org.python.python`. TokenPal's identity is `org.python.python` because the venv's `python` resolves to Homebrew's `Python.app` stub (`/opt/homebrew/opt/python@3.14/Frameworks/Python.framework/Versions/3.14/Resources/Python.app/Contents/MacOS/Python`, bundle id `org.python.python`, ad-hoc signed). The scope contract's "own responsible process" is the operator's outcome; the mechanism that delivers it is a fresh coalition plus an Info.plist id nothing else shares.
- **What gives a process its own identity (specialist probes, 2026-09-06).** The Python.app stub links its framework by absolute path (`otool -l`: `LC_LOAD_DYLIB /opt/homebrew/Cellar/python@3.14/3.14.3_1/…/Python`), so a copy of it at `<X>.app/Contents/MacOS/<exe>` starts and reports `NSBundle.mainBundle().bundleIdentifier()` = X's id (a symlink also works; CFBundle does not resolve it). A shebang script as the bundle executable does NOT work — the kernel execs the interpreter and the main bundle is Python.app. Mutating `NSBundle.mainBundle().infoDictionary()` at runtime changes `NSBundle` but not `NSRunningApplication.currentApplication().bundleIdentifier()`. Venv discovery does not survive on its own (`ModuleNotFoundError`); it does with `Contents/pyvenv.cfg` (`home = <dir of sys._base_executable>`) plus `Contents/lib/python3.14/site-packages` symlinked to the venv's purelib (`/Users/smabe/projects/windoze/.venv/lib/python3.14/site-packages`), after which PySide6 6.11.0 and the editable `tokenpal` import (CPython's `getpath` reads `pyvenv.cfg` from the executable's directory, then its parent). **Control Center keys on the Info.plist id, not the signature:** a byte copy of the stub whose `codesign -dv` still says `Identifier=org.python.python`, in a bundle with Info.plist id `com.tokenpal.probe.stubplain`, launched with `open`, was placed at `(1487, 7)` and painted.
- **Launch mechanics (probed this session).** Only an `open`/LaunchServices launch gets a fresh coalition; exec'ing the bundle executable from a terminal inherits the terminal's coalition and re-poisons the registry. `open -W --stdout <path> --stderr <path> --env VAR=val <bundle> --args …` works with a real path: the terminal's tty device (`os.ttyname(1)`) or a fifo; `/dev/fd/1` fails with `-10810` because launchd, not `open`, spawns the app. The child's cwd is `/`; PATH/HOME/TERM/TERM_PROGRAM and `--env` values are delivered. `open -W` returns 0 even when the child exits non-zero, returns 1 when the child dies before `open` attaches, and SIGINT delivered to `open` kills neither `open` nor the child. `LSUIElement=true` yields `activationPolicy()==1` before any code runs, so `apply_macos_accessory_mode()` (`tokenpal/ui/qt/platform.py:40-75`) becomes a harmless repeat.
- **Consequence for permissions.** Under the bundle, TCC attributes Accessibility / Screen Recording / Microphone grants to `com.tokenpal.app`, not to the terminal. First run after p2 will prompt again, and because the ad-hoc requirement is cdhash-bound, every stub rebuild (Homebrew Python upgrade) prompts again. `responsible_host()` (`tokenpal/desktop/permissions.py:28-36`) and the `--validate` messages (`tokenpal/cli.py:232`, `:251`) currently name `TERM_PROGRAM`, which `open` passes through in the environment — so they would name the wrong app unless the bundle check comes first.
- **Shutdown path.** SIGINT → `_shutdown` (`tokenpal/app.py:1826-1830`) is the only path that runs `overlay.teardown()` → `flush_pending_persist()` (`tokenpal/ui/qt/overlay.py:1040-1050`); `run_loop`'s `finally` only stops the brain (`app.py:1835-1840`), and the tray's Quit calls `app.quit()` directly (`overlay.py:493-495`). p2's Ctrl-C forwarding must therefore deliver SIGINT to the child, not an Apple Quit event.
- **Visibility state today (investigator).** Intent flags `_buddy_user_visible` (`tokenpal/ui/qt/overlay.py:358`) and `_user_visible[name]` (`:376-377`). The dock is derived, never tracked: `_update_dock_placement` (`:1288-1306`) → floating / embedded / hidden. Both flags false ⇒ dock hidden (`:1302-1303`), so the only input surface is gone too. Every hide entry point — tray (`:498-514`), buddy right-click (same `QMenu`, `:1461-1466`), history Hide button (`tokenpal/ui/qt/_log_window.py:113-117` → `_do_toggle_chat`), `/chatlog` (`tokenpal/app.py:676-678` → `toggle_chat_log` `:725`) — funnels through `_toggle_buddy` (`:428-482`) or `_do_toggle_chat` (`:1254-1260`). `restore_visibility_state` (`:964-987`) runs after `setup()` (`tokenpal/app.py:239` → `:255-261`) and before `run_loop` (`:1834`), the persist callback is wired after it (`:257-266`), and `run_loop` re-derives everything from the flags (`:532-596`). Nothing in `tokenpal/brain` reads buddy visibility. The "neither window is coupled" statement originates at `097ee22` as structure, not as a bug fix.
- **Test harness.** No pytest-qt, no offscreen platform, no screenshot harness (grep for `QT_QPA_PLATFORM|pytest-qt|qtbot|grab()|screenshot` over py/toml/sh/md/ini/cfg/yml: only the dock-rotation `grab()` at `overlay.py:1418`). Overlay tests use `QApplication.instance() or QApplication([])` (`tests/test_qt_overlay.py:25-27`), real `QtOverlay(config={}).setup()`, and assert `isHidden()`. `setup()` constructs `BuddyTrayIcon` but only `run_loop` calls `show()` on it (`overlay.py:596`), so the existing suite never creates a status item. Platform helpers are tested with `monkeypatch.setattr("tokenpal.ui.qt.platform.sys.platform", "darwin")` and a fake `sys.modules["AppKit"]` (`tests/test_qt_platform.py:65-95`). Harnesses the Done criteria name exist on this Mac: `/usr/bin/open`, `/usr/bin/osascript`, `/usr/sbin/screencapture`, `/opt/homebrew/bin/rg`, `/usr/bin/pgrep`, `/Applications/Ghostty.app`.

## Parking lot
- **The bundle makes a TCC grant a general-purpose interpreter capability.** `Contents/MacOS/TokenPal` is a byte copy of the Python framework stub, and `open ~/.tokenpal/TokenPal.app --args -c '<python>'` passes arbitrary interpreter arguments through — so anything running as the user inherits whatever Screen Recording / Accessibility / Microphone grants were given to "TokenPal", with no prompt, bypassing every in-process consent gate. Inherent to the locked design: a shebang wrapper does not work (the kernel execs the interpreter and the main bundle becomes Python.app, probed 2026-09-06) and `codesign --force` fails on `Contents/pyvenv.cfg`. Arguably not worse than the status quo it replaces — the grant previously sat on the user's terminal, which runs everything — but it is a real change in what the grant means, and it is the operator's call whether to accept it. Raised by the p2 security-boundary review angle.
- **Audio worker processes now run the bundle stub.** `tokenpal/audio/backends/kokoro.py` and `tokenpal/audio/deps.py` spawn with `sys.executable`, which inside the bundle is `TokenPal.app/Contents/MacOS/TokenPal`. If such a worker registered with LaunchServices it would appear in `running_instances()`, so a lingering one could block the next launch with "TokenPal is already running" and would be SIGINT'd and force-quit by the Ctrl-C path. **Unverified** — the worker is spawned with `subprocess.Popen` rather than through LaunchServices, which is normally what registers an app, and confirming it means launching the bundle. Mitigation if it proves real: spawn workers from `sys._base_executable`.
- **The single-instance guard is machine-wide.** A second checkout with its own `--config` and `data_dir` is declined with "TokenPal is already running" and exit 0, with no hint that the buddy on screen is a different build. That follows from running `open` without `-n` (the locked decision); Windows and Linux still allow two buddies, so the behavior diverges by platform.
- **Piped or redirected output is diverted to a log file.** `open --stdout` needs a real path and `/dev/fd/N` fails with -10810 because launchd spawns the app, so a non-tty stdout goes to `<data_dir>/logs/tokenpal-bundle.log`. `./run.sh --verbose | grep sense` therefore produces nothing on the Qt/macOS path. Mitigated, not fixed: the parent now prints where the output went.
- **`relaunch_in_bundle` always returns 0**, because `open -W` returns 0 even when the app exits non-zero. A wrapper script or CI smoke test can no longer tell a buddy that died at startup from one that ran. Would need a status channel of its own.
- **Orphaned `.TokenPal.app.tmp-*` staging directories.** A SIGKILL between `mkdtemp` and the `finally` leaves one behind and nothing sweeps them. A sweep risks deleting a concurrent launch's staging tree, so it needs a real answer rather than a guess.
- **Auto-show notice.** A one-line status or history message when a surface is shown on the user's behalf. Channels exist (`overlay.py:659-673`); copy and channel are product choices. Not required: the surface itself is the feedback.
- **Tray Quit bypasses `teardown()`.** `overlay.py:493-495` calls `app.quit()` directly, so a toggle inside the 250 ms debounce is lost on tray Quit (historical reviewer, `e9e5f60`). Pre-existing; connecting `aboutToQuit` to `teardown` is a separate one-liner with its own test. **p1 raised the stakes:** the restore repair marks state dirty without arming the debounce timer (by design — `_persist_ui_state` early-returns before the callback is wired), so it reaches disk only through `teardown()`'s flush. A user who launches with an all-hidden state, touches no toggle, and quits from the tray leaves the file unrepaired. Idempotent — the next launch repairs again — so the cost is a repair that never sticks, not corruption. Found independently by three p1 review angles.
- **The sky never starts when a session launches buddy-hidden.** `run_loop:487` is the only `_sky_window.start()`, and it is gated on `_buddy_user_visible` at launch. Quit with the buddy hidden, relaunch, show the buddy → the sky window maps and paints nothing (no sun/moon, no day-night, no precipitation) until the next restart with the buddy visible. Pre-existing — the `_toggle_buddy` closure had the same gap and `{buddy_visible: false, chat: true}` was already reachable — but p1 makes that the ordinary way to leave the app, so it is now much more likely to be hit. Fix is to give `_set_buddy_visible`'s show branch the weather-lifecycle half of `run_loop` (`start()` + the `_reanchor_weather` singleShot). Found by the p1 closing review round.
- **The auto-shown buddy's floating dock takes no focus.** After hiding chat with the buddy hidden, the buddy returns with an unfocused floating dock (`WA_ShowWithoutActivating`), so the next keystroke goes wherever macOS put key status. This is byte-identical to the ordinary buddy-visible steady state, which is why it was not treated as a regression, but two review angles flagged it independently and p1's Done capture (b) types a character to settle whether it feels wrong in practice.
